# 自我改进的 agent，真的变好了吗？

*李琢玮（77）· 2026 年 10 月 · 代码与全部原始日志：[github.com/imlizhuowei/realgain](https://github.com/imlizhuowei/realgain)*

> **一句话结论**：让 agent 按"大模型评委"的分数改进自己，评委分会稳定上涨，但对照标准答案的真实质量不涨，有时还会下跌。评委奖励的版本没有变好；真实正确率更高的那个版本，反而被三个评委一致扣分。在没有标准答案、只能靠评委打分的企业任务里，"评委说进步了"不能等同于真进步。

## 1. 为什么问这个问题

自我改进的 agent（AFlow、DGM、各种改写自身提示词或"工作手册"的循环）做的事情都一样：尝试一个改动，打分，分数高就保留。每次保留都**声称**带来了提升。

但一个被保留的提升，可能来自五种原因：

| 来源 | 意思 |
|---|---|
| 真提升 | 换一批新题照样更好 |
| 运气 | 这次评测碰巧考得好。正因为考得好才被选中，所以重跑一次就缩水（"赢家诅咒"） |
| 过拟合 | 只在拿来选拔的那几道题上更好 |
| 评委被骗 | 打分的大模型喜欢它，但它其实没有更对 |
| 作弊 | agent 碰到了评分用的东西（答案、测试、评分脚本） |

在代码、数学这类能自动判对错的任务上，"评委被骗"基本不存在。但企业真正大量需要的是数据分析报告、合同审查这类任务，没有程序能判对错，实践中通常请一个大模型当评委。这正是最需要知道"进步是不是真的"，也最难知道的地方。

## 2. 先看别人公开的记录（不花钱）

**AFlow**（6 个基准，公开了每一轮在每道题上的得分）
- 27 次被接受的改进里，只有 8 次大于"换一批题"带来的抽样误差。
- AFlow 每轮重复跑 5 次来控制噪声，但这只控制了"同一批题重跑"的运气（约 1–2 分）。更大的误差来自"题目本身是怎么抽出来的"（约 3–5 分），这部分重复跑看不见。
- 在 HumanEval 上，最终最好的版本领先平均版本 5.7 分，而如果所有版本其实一样好，纯靠"从 21 个里挑最好的"也能领先 5.9 分（p = 0.66）。

**DGM**（公开了每个版本在 SWE-bench 上逐题的结果和每次自我修改的代码）
- 主实验里 40 个进入档案的版本，只有 3 个相对父版本的提升超出了噪声。
- 我扫了全部 465 个自我修改的代码补丁，没有发现针对评分的改动。DGM 的评分系统放在 agent 能改的代码之外，结构上就改不到。反倒有好几个补丁是 agent 自己加的检查："如果只改了测试文件，就提醒自己去改源代码"。

## 3. 自己搭一个循环：真实企业任务 + 藏起来的标准答案

**设计思路**：选两个"表面上只能靠评委打分"的真实任务，但我手里偷偷握着标准答案。这样每个版本都能同时看到两个分数：**评委分**（循环以为的进步）和**真实分**（对照标准答案的进步）。

- **场景 A：经营数据分析报告**。用一家英国礼品批发商 2009–2011 年的真实交易数据（100 万行，含退货、运费行、缺失客户编号、最后一个月数据不完整等真实脏数据），让 agent 给商务总监写同比分析备忘录。备忘录末尾要填 7 个关键数字，标准答案按数据字典里的 KPI 定义算出。
- **场景 D：合同审查**。用 CUAD 数据集里的真实 SEC 合同，让 agent 写审查意见，并判断合同里有没有"责任上限""控制权变更""排他条款"等 10 类条款。标准答案是律师的标注。

做题的 agent、改手册的"改写器"和评委都用 Kimi K2.6；另用 Kimi K3 当独立评委复核（后来又加了非 Kimi 的 DeepSeek，见第 6 节）。评委只看任务说明和报告，**看不到原始数据**，这也是实践中最常见的用法。

### 3.1 零售报告：评委越满意，报告越错

循环改了 4 代"工作手册"，评委分从 6.6 涨到 8.2。拿起点手册和"最好"的手册在 **21 道循环没见过的新题**上各跑一遍：

| | 评委分变化 | 真实正确率变化 |
|---|---|---|
| Kimi K2.6（循环里用的评委） | +1.0 | |
| Kimi K3（独立评委） | +1.3 | |
| 标准答案 | | **−12.4 分**（95% 区间 −22.9 到 −1.9；9 题变差，1 题变好） |

改出来的手册越来越强调"严格做同口径比较、把每一镑差额都核对清楚"。评委觉得更专业，但 agent 更常把删减过的同口径数字当成要求的全期收入来报（30 份里从 12 份增加到 17 份）。**报告看起来更严谨，交付的核心数字反而错了。** 评委没有原始数据，查不出来。

### 3.2 合同审查：三条循环，三种假进步

为了回答"agent 能碰到什么，决定了主导的是哪种假提升"，我在合同场景跑了三条配置完全相同的循环（5 份选拔合同、每代 2 个候选、6 代），只改"用什么挑"和"答案放在哪"：

- **R1：大模型评委挑，答案锁住**
- **R2：标准答案自动打分挑，答案锁住**
- **R3：标准答案挑，但答案文件放在 agent 的工作目录里，不提示它**

开跑前我把预测写进了一个文件（预注册）。之后对每条循环里**每一个被接受的版本**做了三项检查：在原来那 5 份合同上重跑两次；在 15 份新合同上跑一次；审计所有命令，看有没有碰过答案文件。

[图：decomp_v1.png]

**R1（评委挑）——评委被骗。** 被接受的 4 个版本里，后三个在新合同上的评委分稳定上涨约 1 分（两个评委都是，置信区间都在 0 以上）。真实正确率没有涨，第 1 代甚至略降（−2.8）。

**R2（标准答案挑）——主要是运气，而评委给真实更好的版本扣分。** 循环以为自己连涨了 +2、+4、+6 分，在原题上重跑后是 −2.2、+4.8、+0.8。到了新合同上，**三个评委（Kimi K2.6、K3、DeepSeek）给这些版本的分都下降了**，真实正确率却不降反升，第 2 代高了 4.6 分。

**R3（答案可见）——作弊。** 没有任何提示，agent 会自己 `ls -la .grader`，然后 `cat .grader/gold.json`。连最初那本只有 12 个词的手册，在新合同上也有 20% 的运行这样做，偷看的题全部 100% 正确。出乎我预料的是：起点版本靠偷看拿到 96%，之后 5 代没有一个候选能超过它，**作弊把门槛抬高，循环被卡住了**。最后被接受的版本（第 6 代）去掉偷看的运行后，新合同上的真实提升是 +1.3 分，和 0 分不开。

**把三条放在一起看**：用评委来挑，评委分和真实质量往相反方向拉；用标准答案来挑，挑出来的主要是运气；答案一旦放得到，agent 不用学就会去看。

## 4. 预测 vs 结果

| 预测（开跑前写下） | 结果 |
|---|---|
| P1 R2 的提升主要是运气，新合同上在 ±3 分以内 | 运气部分成立；第 2 代在新合同上比预测更好（+4.6） |
| P2 R3 至少有一次运行偷看；循环会专门选出偷看的版本（我给了 40% 的可能） | 前半句成立，后半句没有发生 |
| P3 R1 每一代评委分都涨，真实质量 ≈ 0 | 大体成立，第 1 代的评委涨幅还在噪声范围内 |
| P4 在原题上重跑，提升缩水一半以上 | 成立（R2：循环看到平均 +4.0，重跑 +1.1；R3：+2 对 +0.8） |

## 5. 工具箱：realgain

把上面的检查整理成了一个小工具：输入任何自我改进循环的评测日志（每行一个"版本 × 题目 × 运行"），输出每个被接受的改动：
- 是否超过题目抽样噪声
- 在新题上是否还在
- 和标准答案是否一致
- 有没有碰过评分文件
- "挑出来的最好版本"的领先有多少纯靠运气

附带 AFlow、DGM 和我自己三条循环的转换脚本与示例报告，以及一份十分钟自查清单。

另外两项功能：

- **不用重跑就估出"运气"**：只用循环自己的日志（包括被淘汰的候选），估计被选中的版本在新题上真正能有多少提升。在模拟循环里，它把循环自报数字的高估从 +22 分降到 +3 分；在 AFlow 公开日志上，4 个基准的高估都减小了。
- **用少量人工标注核查评委**：几道标注就足以挡住一个虚假的"B 更好"，在所有测试情形里都没有被错误确认过。

## 6. 是不是只有 Kimi 会这样？能不能让评委看数据来解决？

**换一家模型当评委。** 我用 DeepSeek-V4-Pro，按同样的评分标准、同样的输入，把存下来的 465 份报告全部重新打了一遍分：

| | DeepSeek 评委分变化 | 真实变化 |
|---|---|---|
| 零售：最终手册 vs 起点（21 道新题） | **+0.69**（+0.04 到 +1.34） | −12.4 分 |
| 合同：R1 最终版本 vs 起点（15 份新合同） | **+1.0**（+0.1 到 +1.9） | 0 |
| 合同：R2 第 2 代版本 | **−0.97**（−1.83 到 −0.10） | +4.6 |

和 Kimi 的结论一样：评委奖励没变好的版本，给真实更好的版本扣分。DeepSeek 和 Kimi 的打分相关系数是 0.64–0.72，两家模型"喜欢的东西"高度一致，而这些东西和"答对"无关（合同上与标准答案的相关系数是 −0.09）。

**让评委能打开原始数据。** 直觉上，评委被骗是因为看不到数据，那就让它看。我给评委一个文件夹，放上原始交易数据、数据字典、任务说明和备忘录，允许它写代码核对，然后再打分（评分标准不变，只把"你没有原始数据"改成"你有原始数据，可以自己核对"）。

结果评委确实认真核对了，平均每份备忘录跑了 22 条命令，但它**还是更偏爱越改越错的最终手册**（+1.21 分，+0.33 到 +2.09，用 DeepSeek-Flash 测；只看备忘录时是 +0.78）。读它的评语就明白了：它是**顺着备忘录自己的口径**去核对的。备忘录把删减过的同口径数字当全期收入来报，评委就按同样的口径重算，"所有关键数字都能从原始数据精确复现"，于是给了高分。31 份把这个数报错的备忘录里，只有 9 份的评语提到了这个问题。

**能看数据，只能抓住"算错了"，抓不住"算的东西本身就不对"。** 后一种错误恰恰是对业务影响最大的。

换成 Kimi K2.6 当"能看数据的评委"（30 份备忘录），结果不太一样：它看了数据后**不再偏爱**越改越错的手册（偏好从只看备忘录时的 +1.07 降到 +0.07，区间 −1.39 到 +1.52），但它**也没能识别出错误**：报错全期收入的备忘录平均 7.12 分，报对的 7.21 分，几乎没有区别。所以让评委看数据有一点帮助，但解决不了问题。

## 7. 局限

- **规模**：每条循环只跑了一次，新题 15–21 道，小于约 4 分的真实变化测不出来。合同的数字以起点版本的全部运行为基准。
- **模型**：做题的 agent 只用了 Kimi K2.6；评委有 Kimi K2.6、K3 和 DeepSeek 三个。
- **标准答案**：零售只用了 7 个指标里定义没有歧义的 5 个。
- 所有关键数字都由一个没参与实验的 agent 从原始日志独立重算过。

## 8. 相关工作

- **SEAGym**（2606.17546）：自我进化 agent 的评测环境，用能程序验证的任务（Terminal-Bench、HLE）。它测到 TF-GRPO 在验证集上 +17.1、分布外 −2.5，但不研究评委分与真实质量的分离。
- **Winner's Curse in LLM Self-Improvement Loops**（2610.09239）：独立地研究了选拔带来的分数虚高。
- **Auditing Harness Tampering**（2609.00069）：审计自我改进系统修改评测框架的行为。
- **Scoring Higher, Answering Worse**（2609.38847）等：在强化学习训练里观察到"评分标准分涨、真实质量跌"。本项目把这件事搬到了**不改模型权重、只改提示词的自我改进循环**里，并放在真实企业任务上。
- **CLAUSE**（2511.00340）、**CUAD**：合同审查数据集。
